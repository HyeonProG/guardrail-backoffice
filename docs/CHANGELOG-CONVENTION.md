# CHANGELOG 작성 규칙

## 1. 목적
이 문서는 Guardrail 프로젝트의 `CHANGELOG.md` 작성 기준을 정의한다.

이 프로젝트의 changelog는 배포 공지용 문서가 아니라, 기능과 구조 변경 이력을 간단하게 기록하는 문서로 사용한다.

## 2. 작성 방식
- changelog는 간단하게 유지한다.
- 불필요하게 긴 설명은 작성하지 않는다.
- 항목은 한 줄로 작성한다.
- 날짜는 작성하지 않는다.
- `Unreleased` 섹션은 사용하지 않는다.
- 버전은 `0.1.0`부터 시작한다.
- 배포 공지용 형식이나 코드블록 형식은 사용하지 않는다.

## 3. 섹션 구분
changelog는 아래 3개 섹션만 사용한다.

### 추가
- 새로운 기능 추가
- 새로운 문서 추가
- 새로운 설정 추가
- 새로운 구조 도입

### 수정
- 기존 기능 수정
- 설정 변경
- 문서 내용 보완
- 구조 조정
- 의존성 변경

### 삭제
- 더 이상 사용하지 않는 기능 제거
- 불필요한 설정 제거
- 사용하지 않는 문서 제거

## 4. 작성 원칙
- 무엇이 바뀌었는지 바로 이해할 수 있게 작성한다.
- 추상적인 표현보다 구체적인 대상을 적는다.
- 한 작업 흐름에서 변경이 발생하면 가능한 함께 기록한다.
- 첫 버전에서는 필요한 경우 모든 항목을 `추가`로만 기록할 수 있다.

## 5. 권장 예시
```md
# CHANGELOG

## [0.1.0]
### 추가
- `docs/PROJECT-OVERVIEW.md` 문서 추가
- JWT, Querydsl 의존성 추가

### 수정
- `application.yml` 기본 설정 정리
- 문서 파일 네이밍 규칙 대문자 기준으로 통일
```

## 6. 지양할 예시
### 너무 모호한 표현
- 설정 수정
- 문서 변경
- 코드 개선

### 너무 긴 설명
- application.yml 파일 내부에 들어가는 datasource, jpa, logging, jwt 관련 설정을 프로젝트 초기 구동이 가능하도록 전체적으로 정리하고 주석도 함께 수정

## 7. 관리 기준
- 새 버전을 시작할 때 상단에 새 버전 섹션을 추가한다.
- 이전 버전 내용은 유지한다.
- 버전 증가는 `docs/VERSION-POLICY.md` 기준을 따른다.
