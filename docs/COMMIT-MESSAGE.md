# 커밋 메시지 규칙

## 1. 형식
커밋 메시지는 아래 형식을 따른다.

```text
<type>: <설명>
```

규칙은 다음과 같다.

- `type`과 `:` 사이에는 공백을 넣지 않는다.
- `:` 뒤에는 공백 한 칸을 둔다.
- 설명은 짧고 명확하게 작성한다.
- 설명은 한글 또는 영문으로 작성할 수 있다.
- 이슈 번호는 필요할 때만 뒤에 추가한다.

예시:

```text
docs: 초기 프로젝트 문서 추가
feat: 상품 초안 생성 기능 추가
fix: JWT 만료 시간 계산 오류 수정
```

## 2. Type
| Type | 용도 |
|------|------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 리팩토링 |
| `chore` | 빌드, 설정, 의존성, 기타 작업 |
| `docs` | 문서 추가 또는 수정 |
| `test` | 테스트 추가 또는 수정 |
| `style` | 포맷팅, import 정리 등 코드 스타일 변경 |
| `perf` | 성능 개선 |

## 3. 작성 원칙
- 한 커밋은 하나의 의도를 가지도록 작성한다.
- 커밋 메시지는 변경 결과가 바로 이해되게 작성한다.
- 너무 포괄적인 표현보다 구체적인 대상을 포함한다.

예시:

- `docs: 프로젝트 문서 구조 정리`
- `chore: JWT 및 Querydsl 의존성 추가`
- `feat: 상품 설명 생성 요청 API 추가`

## 4. 지양할 예시
- `fix: 수정`
- `docs: 문서 수정`
- `chore: 이것저것 정리`

## 5. 현재 프로젝트에서 자주 사용할 타입
초기 단계에서는 아래 타입을 주로 사용한다.

- `docs`
- `chore`
- `feat`
- `refactor`

## 6. 예시
```text
docs: 초기 프로젝트 문서 및 changelog 규칙 추가
chore: JWT 및 Querydsl 초기 의존성 추가
feat: User 도메인 엔티티 추가
refactor: 패키지 구조를 도메인 기준으로 정리
```
